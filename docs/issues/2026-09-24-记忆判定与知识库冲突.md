## 问题是怎么被发现的

起因是问「文件内容冲突怎么解决」。核查时发现知识库层面**完全没有**冲突处理机制
（对比：长期记忆有一整套矛盾消解），于是造两份互相矛盾的文档实测。
实验过程中顺带验证了记忆侧的边界，结果查出一个比知识库问题更严重的缺陷。

## 问题 1：改口但没说「改成」，系统会一直记着过时的值

### 现象

用本地探测脚本（不需要调用模型）复现：

```js
await m.add({ text: "本项目的向量库代号是 ZTX-9917", ts: t });
await m.add({ text: "本项目的向量库代号是 ZTX-8800", ts: t + 1 });
```

修复前的输出：

```
库里剩下: 本项目的向量库代号是 ZTX-9917 | confidence=0.7
检索「向量库代号」→ 本项目的向量库代号是 ZTX-9917
```

新值被当成重复**直接丢弃**，旧值反而被强化。也就是说：用户改口之后，
系统会越来越自信地记着错的东西。

### 根因

`src/memory/lifecycle.ts` 的 `add()` 把「没有推翻词」等同于「是重复」：

```ts
// 修复前
if (nearest && !conflicting && nearest.overlap >= this.duplicateThreshold) {
  this.reinforce(nearest.memory, now);
  await this.persist();
  return;            // ← 新值在这里被丢掉
}
```

但「代号是 ZTX-9917」与「代号是 ZTX-8800」是**同一模板换了值**，属于更正而非重复。
两者的 token 重叠高达 0.96（只差一个数字 token），稳稳越过 0.85 的去重阈值。

对比一下：含推翻词的更正（「代号**改成** ZTX-8800」）能正确触发矛盾消解——
问题只出在**没有语言线索**的改口上。

### 为什么严重

这不是「答案不够好」，而是**记住了错误的事实**，且会随时间越来越固化
（每次召回都强化错误值）。相比之下，知识库那边只是「答得不全」。

### 修复

新增一层「基础 token」比较，区分「换个说法」与「内容被换掉」。
基础 token 指中文单字与拉丁词，**丢掉相邻双字**——因为双字组会让两种情况的字面重叠度
变得一样高，退到单字粒度才分得开。

```ts
// src/memory/textIndex.ts
export function baseTokens(tokens: string[]): Set<string> {
  // 跳过由两个及以上 CJK 字符拼成的相邻双字
}
```

```ts
// src/memory/lifecycle.ts
function compareFacts(next, previous): { replaced: boolean; keepsAll: boolean } {
  const lost   = 旧有 token 不在新里;
  const gained = 新有 token 不在旧里;
  return { replaced: lost && gained, keepsAll: !lost };
}
```

四种情况各有正确归宿：

| 场景 | 旧信息丢失 | 新信息引入 | 判定 | 结果 |
|---|---|---|---|---|
| 原样重复 | ✗ | ✗ | 重复 | 只强化，保持 1 条 |
| 纯补全 | ✗ | ✓ | 重复 | **文本刷新为更全的版本** |
| 纯缩减 | ✓ | ✗ | 重复 | 保留更完整的旧文本 |
| **改值** | ✓ | ✓ | **替换 → 旧记录作废** | 只剩新值 |

两个判定分支都要改，只改一处不够：

- **去重分支**加 `!replaced` 排除条件——否则新值仍被丢弃
- **矛盾消解分支**把 `replaced` 也作为触发条件——否则旧值不作废，两条冲突值并存，
  检索时会互相污染

另外，判为重复时若新记忆信息更全，用它的文本刷新旧记录，避免丢掉补充进来的信息
（例如「部署在北京」→「部署在北京和上海」）。

### 验证

```
矛盾消解：「...ZTX-9917」已被「...ZTX-8800」取代（由信息替换判定触发，无推翻词）
【改值·无推翻词】库里: ...ZTX-8800        检索: ...ZTX-8800
【补全】         库里: 项目部署在北京和上海
【完全重复】     条数: 1 | confidence: 0.7
```

单测新增 4 条：改值 / 补全 / 信息缩减 / baseTokens 粒度。

## 问题 2：知识库内部冲突无人裁决

### 现象

造两份互相矛盾的文档做实测（具体值从略，见文首说明）：

**无时间线索时**——模型拒绝选，并列报出两边内容与来源，要求人工确认：

```
知识库中该问题存在两条冲突记载：`A.md`「某小节」写的是……，而 `B.md`「某小节」写的是……，
两者均注明……，需确认以哪一份为准。
```

**文件名带日期时**——模型自行裁决并说明依据：

```
> 注：早期《xxx-2026-01-01》曾规定为……，已被更新的《xxx-2026-09-01》取代，以最新版本为准。
```

两次表现都不错，但**没有一行代码保证它**。

### 根因

- `KnowledgeChunk` 只有 `id / source / heading / text`，**连时间字段都没有**——
  `mtime` 在扫描文件时拿到了，却从没进过片段
- 检索打分为 `余弦 × 长度惩罚`，没有任何"新旧优先"或"一致性"判断
- 提示词对知识库冲突零约束（`recalled_memory` 段那句只管长期记忆）

知识库被设计为"静态、不遗忘的事实源"，不共用记忆那套生命周期规则——这是有意的，
代价就是冲突无人裁决。

### 为什么"模型自己兜住"不算解决

三个具体风险：

1. **冲突能否被发现，取决于两份是否都进 `top_k`。** 实测中冲突两份的分数只差 **0.0013**，
   纯属巧合才双双入榜。若一方因措辞差异排到第 5 位而 `top_k=4`，模型只会看到一份，
   然后**毫不犹豫地把它当唯一事实**——这是最大的漏洞
2. **行为是涌现的，不是被保证的。** 上述好表现是模型自发的，一次提示词改动就可能退化
3. **时间线索依赖文件名约定。** 文件名不带日期时，就退化成"无法判断新旧"

### 修复（3 项）

**2a. 提示词约束——把自发的好行为固化**

`search_knowledge` 的工具描述（会进入每次请求的 tools payload）：

> 若多个片段对同一问题给出互相矛盾的说法：先比较 `updated_at`，以较新的记载为准；
> 若无法判断新旧（日期相同或缺失），不要自行裁决，应并列列出冲突内容与各自来源，
> 并说明需要以哪一份为准——片段顺序只反映词面相关度，不代表权威性。

**2b. 片段带上文件修改时间**

`KnowledgeChunk` 新增 `updatedAt`（毫秒，来自 `file.mtimeMs`），工具返回时转成
`updated_at: "YYYY-MM-DD"`（本地时区，只到日期——够判新旧且省 token）。
这样模型判新旧不再依赖"文件名里恰好有日期"。

**2c. 同主题片段补入，避免冲突方被 `top_k` 截掉**

检索截断后，把「`heading` 相同但 `source` 不同」的片段补回来。只补跨文档的：
同一文档同一小节的后续分块是内容延续，不算另一份记载，补进来只是白烧 token。
补入数量以 `top_k` 为上限，避免结果整体翻倍。

### 验证

单测新增 4 条：片段带 `updatedAt`、`top_k=1` 时同主题冲突方被补回、
同源同标题不补、工具返回含 `updated_at`。

## 问题 3：会话列表排序测试 flaky（顺带修）

跑全量测试时 `tests/history.test.ts` 偶发失败：断言「列表按最近更新倒序」，
但两个会话在同一毫秒内写入时 `updatedAt` 相等，排序退化为任意顺序。

这是**测试自身的隐患**（不是产品缺陷）。修法是拉开 5ms 间隔使其确定性成立，
并连跑两次确认不再 flaky。
