# 上下文处理补全：摘要措辞保护 / 预算按窗口推导 / 卸载 / 子 agent

日期：2026-09-24
范围：Agent 上下文处理（对应业界 context engineering 的四类做法）
状态：四项全部完成并验证

> 本文放在 `docs/` 下，而 `docs/` 是知识库根目录，因此这份记录也会被索引进知识库。
> 描述实验时故意不复述具体的业务值，避免示例值被当成真实规范召回。

## 背景

起因是一次「Agent 的上下文怎么处理、业界有哪些方案」的盘点。盘点结论是四类做法
（Reduce 压缩 / Offload 卸载 / Retrieve 按需 / Isolate 隔离）里，本项目只做全了
Reduce 与 Retrieve，Offload 与 Isolate 完全没有，而 Reduce 里还有两个具体缺口：

- 摘要 prompt 只要求保留「目标/结论/未决问题」，**没有保护精确措辞**。
  对照研究里的 *Compaction Cliff*：安全规则经过一轮压缩只剩 53%，五轮后剩 10%——
  因为规则需要逐字精确才可执行，而日志摘要一下没关系，两者却被同等压缩。
- 滑窗预算写死成绝对 token 数（6000），换模型必须手改。

## 改动一：摘要保护精确措辞

`src/memory/summary.ts` 的压缩 prompt 改为**两节输出**：

- `【指令与约束】`——用户明确提出过的要求、规则、禁止事项，**逐字引用原文**，
  不要改写、不要概括、不要把同义表述合并；没有就写「无」
- `【摘要】`——只保留三类信息（目标与偏好 / 已确认结论 / 未决问题）

用「【】」标签而不是 Markdown 标题，是为了不与 `## 早前对话摘要` 的层级打架。

## 改动二：预算按模型窗口推导

`src/core/config.ts`：

| 配置 | 默认 | 说明 |
|---|---|---|
| `MINIAGENT_MODEL_CONTEXT_TOKENS` | `131072` | 模型窗口（DeepSeek-V3.2 官方标称 128K） |
| `MINIAGENT_MEMORY_BUDGET_RATIO` | `0.25` | 历史预算占窗口的比例 |
| `MINIAGENT_MEMORY_MAX_TOKENS` | `0` | 显式写死预算；`>0` 时优先于上面两项 |

推导：`131072 × 0.25 = 32768`。**换模型只改窗口，预算自动跟着变。**

比例取 0.25 而不是更高，是因为 context rot 的研究显示输入越长质量越差、成本也越高，
需要给 system、工具回灌与输出留出余量。

摘要触发阈值 `MINIAGENT_MEMORY_SUMMARY_THRESHOLD` **刻意保持绝对值**（2000）不随窗口伸缩：
它衡量的是「裁掉的内容够不够抵一次 LLM 调用」，是成本考量，与模型窗口无关。

## 改动三：工具结果卸载（Offload）

原来是超限即截断，**内容永久丢掉**。现在改为卸载：

- 完整内容写入 `workspace/offload/<runId>/<tool>-<callId>.txt`
- 上下文里只留「前 N 字符预览 + 完整长度 + 路径」
- agent 需要细节时用 `read_file` 取回——文件沙箱的根就是 `workspace`，路径天然可达
- **写盘失败退化为纯截断**：卸载只是优化，不该成为对话的故障点

## 改动四：子 agent 隔离（Isolate）

新增 `run_subagent` 工具（`src/tools/builtins/subagent.ts`）：

- 子 agent 用**独立上下文**，中间的检索/读文件都留在它自己那边，父只拿结论与用量
- 子 agent 的工具集是「除 `run_subagent` 以外的全部工具」，**递归深度天然为 1**
- 子 agent 不挂记忆与长期召回——独立干净的上下文正是它的意义
- 超时用**协作式取消**（`context.requestCancel()`）而不是运行时的硬超时：
  `Promise.race` 只是丢弃结果，底层任务仍在跑，子 agent 会变成后台孤儿
- 为此给工具加了可选的 `timeoutSeconds`：本工具声明 `subagentTimeout + 30s`，
  保证先由「取消」收尾而不是被硬超时切断

## 验证

**单元测试**：170 个全部通过（本轮新增 12 个），`tsc --noEmit` 零错误。

**端到端实测**（真实调用模型，让它派子 agent 去查三件事）：

| | 迭代 | token | 耗时 |
|---|---|---|---|
| 子 agent | 4 轮 | **50,280** | 11.68s |
| 父 agent | 1 轮 | **8,936** | 17.75s |

子 agent 内部翻了多个文档、跑了 4 轮检索，消耗 5 万 token；父 agent 只用了 1 轮 8936 token——
**那 5 万 token 的探索一步都没进父的上下文**，这就是 Isolate 的收益。父的最终答案质量依然完整，
还自行判断出「两处来源描述一致，无冲突」。

**评测回归**：`npm run eval` 6/6 通过。平均 prompt token 从 4059 升到 4722，
原因是工具列表多了 `run_subagent`（它的描述较长）。

## 需要注意的连带影响

**历史预算从 6000 变成 32768（5.5 倍）。** 这是「改百分比」的直接结果，不是 bug：

- 长对话能保留更多原文，更晚触发摘要（更连贯）
- 但每次请求的输入 token 变多，成本随之上升

若觉得太大，调 `MINIAGENT_MEMORY_BUDGET_RATIO`（如 0.1 ≈ 13K）或直接写死
`MINIAGENT_MEMORY_MAX_TOKENS`。

## 实现中发现的一个架构约束

子 agent **自建事件总线**，所以它的中间步骤不进父的轨迹（父只看到结论与用量）。

根因：server 的事件总线是**按请求创建**的（避免并发串台），而工具注册表在**启动时**就建好了，
工具闭包里拿不到当次请求的总线。要打通得引入作用域传递机制（如用 `AsyncLocalStorage` 携带 bus）。

三个候选解法的代价对比与当前选择（维持现状）已写入设计方案第 10 节的
「约束详解：子 agent 的中间步骤不进父轨迹」，此处不重复。
当前把子 agent 的轮数与 token 作为工具返回值上报，成本可见、步骤不可见。
