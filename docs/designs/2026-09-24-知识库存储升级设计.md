# 知识库存储升级设计方案：三层分离 + 向量检索

日期：2026-09-24
状态：**设计方案；一期、二期已按「本地化变体」实施，四期做了重建与对账**（见文末第 12 节）
范围：把知识库从「内存 TF-IDF」升级到业界的标准形态
前置阅读：[主设计文档](../superpowers/specs/2026-09-23-miniagent-design.md) 第 6 节「上下文处理」

> 本文放在 `docs/` 下，会随知识库一起被索引。
>
> **本文描述的是目标形态（Postgres + pgvector + 对象存储的三层分离）**，一期实际落地时按项目真实规模做了取舍，
> 与本文的差异集中在第 12 节，读第 4–9 节的容量与运维分析时请以「目标形态」理解。

## 1. 为什么需要这份设计

现有知识库（`src/knowledge/`）的形态是：

- 源文件直接在文件系统，**零复制**
- chunk 与索引**全在内存**，按「路径 + mtime」指纹惰性重建
- 检索是**词面 TF-IDF**，跨语言与同义改写都会零召回

第三点是硬伤，已记在 spec 的已知缺口里。本方案给出升级路径，并按用户要求明确**缺陷**与**最大可负载量级**。

## 2. 设计原则（抄业界共识，不自己发明）

1. **三层分工**：源文件 / 元数据 / 向量分开存，因为三者访问模式完全不同
2. **计算下推**：解析从对象存储并发拉取，切片与嵌入后流式写入向量库，数据库不承受大文件 I/O
3. **先过滤再检索**：元数据过滤条件（租户、状态、语言、时间）必须能和向量检索在**同一条 SQL** 里完成
4. **嵌入模型比向量库重要**：好库配差模型召回很差，普通库配好模型召回很好
5. **不上专用向量库**：1000 万向量以下，pgvector 的运维优势压过专用库的性能优势

## 3. 总体架构

```
                     ┌──────────── 写路径（离线/增量）────────────┐
  [原始文档]  ──上传──▶ 对象存储（S3 / MinIO）
      │                  键：knowledge/{tenant}/{doc_id}/raw.pdf
      │                  前端访问走预签名 URL
      ▼
  解析 Worker（并发拉取、OCR、表格转 Markdown）
      │
      ▼
  切分（标题/段落两级，600 字 + 80 字重叠）
      │
      ▼
  Embedding（批量，1536 维）
      │
      ▼
  ┌──────────────────────────────────────────────────────┐
  │ PostgreSQL                                            │
  │  documents  ← 元数据、权限、解析状态、对象存储键      │
  │  chunks     ← chunk 文本 + 向量 + 外键 → documents    │
  │               HNSW 索引（halfvec）                    │
  └──────────────────────────────────────────────────────┘

                     ┌──────────── 读路径（在线）──────────────┐
  [用户问题] ──▶ Embedding ──▶ 一条 SQL：
                              过滤（tenant/status/语言）
                              + 向量检索（HNSW）
                              + JOIN documents 取标题与出处
                              ORDER BY embedding <=> $1 LIMIT k
                     ──▶ 取回 chunk 文本 ──▶ 重排（可选）──▶ 拼入 prompt
```

关键点：**过滤、检索、取元数据是一次查询、一次往返、一个事务**。这是 pgvector 相对专用向量库最实在的优势——专用库需要把 `tenant_id`/`status` 反范式化写进它的 metadata 并永久保持同步。

## 4. 存储层设计

### 4.1 源文件（对象存储）

| 项 | 设计 |
|---|---|
| 存储 | S3 兼容（本地 MinIO，云端 OSS / R2 / S3） |
| 键设计 | `knowledge/{tenant_id}/{doc_id}/raw.{ext}`，`{doc_id}` 用内容哈希 |
| 为什么用内容哈希 | 同一文件重复上传天然幂等；换个文件名不会重复入库 |
| 中间产物 | 解析出的图片、OCR 原图同桶存放：`.../assets/{page}-{n}.png` |
| 访问 | 不给公开 URL，一律预签名 URL（前端直接读） |
| 生命周期 | 冷数据可转低频/归档存储，**不影响检索**（检索只读 chunk 文本） |

### 4.2 元数据（PostgreSQL）

```sql
CREATE TABLE documents (
  id            uuid PRIMARY KEY,
  tenant_id     text NOT NULL,
  title         text NOT NULL,
  source_uri    text NOT NULL,          -- 对象存储键
  content_hash  text NOT NULL,          -- 去重与幂等
  mime_type     text NOT NULL,
  size_bytes    bigint NOT NULL,
  status        text NOT NULL DEFAULT 'pending',  -- pending/parsing/ready/failed
  version       int  NOT NULL DEFAULT 1,
  language      text,
  tags          text[] DEFAULT '{}',
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, content_hash)
);

CREATE INDEX ON documents (tenant_id, status);
CREATE INDEX ON documents USING gin (tags);
```

### 4.3 chunk 与向量

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE chunks (
  id           bigserial PRIMARY KEY,
  document_id  uuid NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  tenant_id    text NOT NULL,           -- 反范式化：过滤时不 JOIN
  chunk_index  int  NOT NULL,
  heading      text NOT NULL DEFAULT '',
  content      text NOT NULL,
  token_count  int  NOT NULL,
  -- halfvec：1536 维下存储与索引内存减半，recall 损失 < 0.5%
  embedding    halfvec(1536) NOT NULL,
  tsv          tsvector,                -- 混合检索用（BM25/全文）
  created_at   timestamptz NOT NULL DEFAULT now(),
  UNIQUE (document_id, chunk_index)
);

-- HNSW：m 与 ef_construction 取 pgvector 默认值（16 / 64），是合理的起点
CREATE INDEX chunks_embedding_idx ON chunks
  USING hnsw (embedding halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);

CREATE INDEX chunks_tsv_idx ON chunks USING gin (tsv);
CREATE INDEX chunks_tenant_idx ON chunks (tenant_id);
```

**为什么用 `halfvec` 而不是 `vector`**：1536 维的 `vector` 类型只能索引到 2000 维（索引元组必须塞进 Postgres 的 8 KB 页），`halfvec` 把上限翻到 4000 维，同时存储与索引内存**减半**——`halfvec(1536)` 是当前性价比最高的选择。

**为什么 `tenant_id` 冗余在 chunks 上**：过滤要在向量检索的同一条 SQL 里完成，JOIN 会让优化器难以先过滤再检索。

### 4.4 为什么要 `ON DELETE CASCADE`

源文件删除 → `documents` 行删 → chunks 自动删。这是**引用完整性的最低保障**，避免出现"指向已删文档的孤儿向量"。

## 5. 写入流程

```
1. 上传原件 → 算内容哈希 → upsert documents（相同哈希直接返回，幂等）
2. 解析（PDF/OCR/表格）→ 产出纯文本 + 图片资源
3. 切分（标题/段落两级，600 字 + 80 字重叠）
4. 批量 Embedding（按 100~500 条一批）
5. 事务内：删除该 document_id 的旧 chunks → 批量插入新 chunks
6. 更新 documents.status = 'ready'
```

三个必须处理的点：

- **更新即重建**：文档内容变了，整篇重新切分嵌入（不要尝试 diff 级别增量——切分边界会移位，diff 无意义）
- **删除用 CASCADE**，不要软删了事，否则向量索引越积越大
- **HNSW churn**：频繁增删会让图结构退化，需要定期 `REINDEX INDEX CONCURRENTLY` + `VACUUM`

## 6. 检索流程

```sql
BEGIN;
SET LOCAL hnsw.ef_search = 80;          -- 注意是 SET LOCAL，不是 SET

WITH candidates AS (
  SELECT c.id, c.document_id, c.heading, c.content,
         c.embedding <=> $1 AS distance,
         row_number() OVER (ORDER BY c.embedding <=> $1) AS rn
  FROM chunks c
  WHERE c.tenant_id = $2               -- 先过滤
    AND c.document_id IN (SELECT id FROM documents WHERE status = 'ready')
  ORDER BY c.embedding <=> $1
  LIMIT 30                             -- 多取一些给重排
)
SELECT d.title, d.source_uri, c.heading, c.content, c.distance
FROM candidates c JOIN documents d ON d.id = c.document_id
ORDER BY c.rn LIMIT 8;
COMMIT;
```

三个实战要点：

1. **必须用 `SET LOCAL`**。多数托管 Postgres 前面挂着 PgBouncer（事务池模式），session 级的 `SET hnsw.ef_search` 会被**静默丢弃**——检索仍然"能用"，只是跑在默认 recall 上，而且没有任何日志。
2. **过滤 + 检索的组合**：pgvector 0.8 的 `hnsw.iterative_scan = 'relaxed_order'` 解决"过滤后结果集被吃空"的经典问题（高选择性过滤下 ANN 可能返回不足 k 条）。
3. **重排是可选加分项**：候选 30 条过一遍 cross-encoder rerank，取前 8 条进 prompt。检索质量提升明显，但要额外一个模型。

**混合检索**（向量 + 关键词）：对精确匹配（代号、编号、人名）关键词更可靠。做法是向量 top-20 与 `tsvector` top-20 用 RRF 融合。面向本项目这种"项目文档 + 代号"的场景，**建议第一期就做**。

## 7. 与现有代码的对接

现有 `KnowledgeBase` 接口就是为这种替换留的：

```ts
export interface KnowledgeBase {
  docs(): Promise<Array<{ source: string; chunks: number }>>;
  search(query: string, topK?: number): Promise<KnowledgeHit[]>;
}
```

新增 `PgVectorKnowledgeBase implements KnowledgeBase` 即可，**`search_knowledge` 工具、冲突可见性逻辑、Agent 全都不用改**。要在工厂里改的只有一行：

```ts
export function createKnowledgeBase(settings: Settings): KnowledgeBase {
  return settings.knowledgeBackend === "pgvector"
    ? new PgVectorKnowledgeBase(...)
    : new LexicalKnowledgeBase(...);   // 保留词面实现作为降级
}
```

**建议保留词面实现**作为零依赖降级路径（没配数据库时自动回退），这样"零依赖可跑"的特性不会丢。

`KnowledgeChunk` 需要补两个字段：`page`（页码，用于精确引用）、`documentId`（指回 documents）。

## 8. 缺陷与风险

这一节是重点——引入这套架构**不是纯收益**。

### 8.1 破坏"零依赖"原则（最大的代价）

本项目现在运行时就 2 个依赖（zod、zod-to-json-schema），没有外部服务。引入后需要：

- PostgreSQL 18 + pgvector 0.8.2+
- 对象存储（本地 MinIO，或云端 OSS/S3）
- Embedding 服务（API 或本地模型）
- 解析服务（PDF/OCR，可能还要 Python 侧）

从"双击 npm start 就跑"变成"先 docker compose up"。**这是性质变化**，不只是加功能。建议用 docker compose 封装，并把 pgvector 设为可选后端。

### 8.2 元数据漂移（现在反而没有这个问题）

这是最容易被忽略的一条。现状下**文件系统是唯一事实源**，不存在同步问题。引入数据库后就有两份状态：

- 文件改了但没重新入库 → 检索到旧 chunk
- 文件删了但 DB 没删 → 孤儿向量
- 入库失败（解析报错）但 documents 行已经写入 → 状态是脏的

需要**对账机制**：定期扫描源目录与 `documents` 表比对，找出缺失/多余/哈希不符的条目。这是新增的运维负担。

### 8.3 索引构建的内存墙（比服务的内存墙更低）

反直觉但很重要：**能服务的向量数 > 能构建的向量数**。

实测数据：8 vCPU / 16 GB 的机器能构建 100 万 × 1536 维的 HNSW（约 9 分钟），但**200 万索引在同一台机器上根本建不起来**。构建前必须：

```sql
SET maintenance_work_mem = '2GB';   -- 不足会溢出磁盘，慢 10~100 倍
SET max_parallel_maintenance_workers = 4;
```

### 8.4 HNSW 索引必须常驻内存

索引不进内存不会报错，只是**查询退化到磁盘 I/O**——表现为"平时 20ms，数据涨到某个点后突然 500ms+"。需要 `shared_buffers ≥ 1.5 × 最大索引大小`，并监控索引大小与命中率。

### 8.5 成本

| 项 | 估算 | 说明 |
|---|---|---|
| Embedding（一次性） | 100 万 chunk × 400 token = 4 亿 token ≈ **$8**（text-embedding-3-small） | 便宜，但**每次文档更新都要重嵌入** |
| 数据库 | 单机 16C32G ≈ $150-400/月（云） | 自托管则只是机器成本 |
| 对象存储 | 每 GB 成本的几分之一 | 可忽略 |
| 运维人力 | **最贵的一项** | 迁移、备份、监控、版本升级、索引重建 |

### 8.6 其他具体风险

- **维度上限**：`vector` 类型索引上限 2000 维；换更大的嵌入模型（3072 维）必须用 `halfvec`（4000 维）或降维
- **版本下限**：2026 年有 CVE-2026-3172，pgvector 需 ≥ 0.8.2
- **连接池**：向量检索是重查询，连接池耗尽会拖垮整个 Postgres（包括业务表的读写）
- **不迁移到专用向量库的理由会变**：超过 5000 万向量时，专用库的架构优势（分片索引、DiskANN、乘积量化）是真实存在的
- **如果文档量很小（几千 chunk），这套架构完全不值得** —— 现有内存方案更快更简单

### 8.7 什么时候不该升级

- chunk 总数 < 1 万 → 现状足够
- 纯中文语料且查询词与文档用词一致 → 词面检索够用
- 没有运维能力承接一个数据库 → 先考虑托管服务

## 9. 容量与负载上限

### 9.1 假设与口径

- 嵌入维度 **1536**（`halfvec`，减半后的口径）
- 每个 chunk 平均 **400 token**、约 600 字
- 查询口径 **p95 < 100 ms**，`ef_search = 40`
- 单机 PostgreSQL，索引常驻内存

### 9.2 核心结论：内存决定一切

100 万 × 1536 维的内存账（float32）：

| 组成 | 大小 |
|---|---|
| 表数据（向量本身） | 5.8 GB |
| HNSW 索引（m=16） | 4.8 GB |
| **合计** | **约 10.6 GB / 百万向量** |

`halfvec` 把它压到 **约 5.3 GB / 百万向量**。

据此推算单机能服务的向量数（留一半内存给 OS 与 Postgres 常规负载）：

| 机器 | float32 | **halfvec（推荐）** | 查询 p95 |
|---|---|---|---|
| 4C 8G | ~40 万 | ~80 万 | <50 ms |
| 8C 16G | ~80 万 | ~160 万 | <80 ms |
| 16C 32G | ~160 万 | ~320 万 | <100 ms |
| 32C 64G | ~320 万 | ~640 万 | <120 ms |
| 64C 128G | ~640 万 | **~1200 万** | <150 ms |

对照外部实测：4 GB 节点约 35 万、8 GB 约 60 万、16 GB 约 100 万（同一量级，我的估算略乐观，实际留 20% 余量更稳）。

### 9.3 构建上限（更硬的墙）

| 向量数 | 构建时间 | 最低内存 | 备注 |
|---|---|---|---|
| 100 万 | 单线程 ~25 分钟；4 workers **~9 分钟** | 16 GB | 8C16G 实测可行 |
| 200 万 | ~20 分钟 | **> 16 GB** | 16 GB 机器构建失败 |
| 500 万 | 单线程 >2 小时；并行 **~35 分钟** | 64 GB+ | 需要维护窗口 |
| 1000 万 | 数小时 | 128 GB+ | 需评估是否分区 |

**所以规划容量时要以「构建能力」为准，而不是「服务能力」。** 建议单机不超过 1000 万向量，超过就分区。

### 9.4 各维度的上限汇总

| 维度 | 上限 | 瓶颈在哪 |
|---|---|---|
| 源文件数量 | 无实际上限（对象存储） | 单文件 S3 限 5 TB |
| 单个文件的 chunk 数 | 建议 ≤ 5 万 | 超过后单文件重建耗时长（更新即整篇重嵌入） |
| chunk 文本总量 | 32 TB / 未分区表，分区表可数千分区 | 磁盘 |
| **向量条数（单机）** | **500 万 ~ 1000 万** | **HNSW 构建与常驻内存** |
| 向量条数（分区 + 分片） | 亿级（有公开案例做到 76 亿向量 / 46 TB） | 需按租户/时间分区，且每分区独立索引 |
| 向量维度 | `vector` ≤ 2000；`halfvec` ≤ 4000；二值量化 ≤ 64000 | **索引元组要装进 8 KB 页** |
| 查询 QPS | 单机 **50 ~ 200 QPS**（p95 < 100 ms） | 距离计算吃 CPU + 连接池 |
| 并发写 | 建议批量 upsert，避免高频小事务 | HNSW 增量插入的图结构抖动 |
| 查询延迟 | 百万级 p95 **10 ~ 50 ms** | 超出需加副本；只读副本可线性扩 |

### 9.5 超大规模怎么走（有公开先例）

一个真实案例：某法律语义检索系统用 **Aurora PostgreSQL + pgvector** 承载了 **25 亿文档、76 亿向量、46 TB**，亚秒级查询。做法是：

1. **按租户 hash 分区**，每个租户一个独立 HNSW 索引（逻辑隔离 + 单索引规模可控）
2. **用紧凑嵌入**（降维 / 量化）压成本
3. 单表原型阶段曾试到 76 亿向量，最终靠分区落地

结论：**pgvector 不是不能上亿级，但那时它已经不是"单机加个扩展"，而是一套分区 + 分片的架构**。到那个量级，专用向量库（Milvus / Qdrant 的分片索引、DiskANN）反而是更省力的选择。

### 9.6 什么时候该换方案

| 信号 | 说明 | 动作 |
|---|---|---|
| 向量数 > 1000 万 | 单机构建与内存都吃紧 | 按租户/时间分区 |
| 向量数 > 5000 万 | 分区也开始吃力 | 评估专用向量库 |
| 查询 p95 > 100 ms 且 EXPLAIN 显示磁盘扫描 | 索引没常驻内存 | 加内存 / 上 halfvec / 降维 |
| 构建时间超出维护窗口 | 无法在窗口内重建 | 分区并行构建 / 换 DiskANN 类方案 |
| 高选择性过滤下 recall 崩了 | 过滤吃掉了结果集 | 开 `iterative_scan` / 改分区策略 |
| 写入频率远高于读取 | HNSW churn 严重 | 考虑 IVFFlat 或批量重建 |

## 10. 分期实施建议

| 期 | 内容 | 产出 | 状态 |
|---|---|---|---|
| **一期** | 只加向量检索，**不做对象存储**（源文件继续放文件系统），词面实现保留并行 | 端到端跑通、能验证语义召回是否真的改善 | ✅ 用 LanceDB + 本地模型落地，见第 12 节 |
| **二期** | 加混合检索（向量 + 词面 + RRF）与重排 | 精确匹配（代号、编号）不再漏 | ✅ RRF 已做；cross-encoder 重排评估后未做（理由见第 12 节） |
| **三期** | 引入对象存储 + 解析 Worker + 对账机制 | 支持二进制文档与多租户 | ⬜ 未做（对象存储与 Worker 在本项目规模下不划算，见第 12 节） |
| **四期** | 分区与容量治理、监控与索引重建流程 | 上生产规模 | 🟡 只做了「重建 + 对账」（`npm run knowledge:reindex [--check]`）；分区与增量压实未做 |

**建议至少做完一期再决定要不要继续**。一期的成本最低，且能直接回答"语义召回到底改善了多少"这个根本问题——如果改善不明显，后面三期都不必做。

## 12. 一期 / 二期 / 四期实施记录（本地化变体）

一期解决的是同一个问题——**词面检索的召回失效**——但组件按项目真实规模换了实现：

| 设计里的组件 | 一期实际用的 | 换的理由 |
|---|---|---|
| PostgreSQL + pgvector | **LanceDB**（npm 嵌入式，本地目录） | 本项目知识库是几十个文档、几百个片段（当前 `./docs` 全量 92 片段），pgvector 的运维优势在这个量级换不回「要起一个数据库」的代价 |
| ON DELETE CASCADE 等关系约束 | 应用层按「路径 + mtime」指纹做增量与删除同步 | 没有数据库，一致性由索引时的对比逻辑保证 |
| 对象存储（源文件副本） | **不复制**，源文件继续放文件系统 | 单机场景下副本只带来漂移风险，无明显收益 |
| Embedding 服务（API） | **本地 ONNX 模型**（`@huggingface/transformers`，`Xenova/paraphrase-multilingual-MiniLM-L12-v2`） | 零 API 成本、数据不出本机；代价是首建索引慢，因此增量索引从「优化」变成「必需」 |
| 解析 Worker | 沿用原有 `npm run knowledge:add` | 未做多租户与异步任务，不需要 Worker 形态 |

**保住的**：`KnowledgeBase` 接口不变，`search_knowledge` 工具与 Agent 零改动；
`lexical` 词面实现保留为**默认与降级路径**——两个可选依赖都是「只引类型 + 动态 `import()`」，
实测把 `node_modules/@lancedb` 整个移走后词面检索照常工作，所以「零依赖可跑」这条性质没丢。

**实测结果**（详见主文档 6.1）：跨语言零召回问题消除。
语料是**受控构造的双语夹具**（英文 `security.md` + 中文 `governance.md`）——
项目自有语料全是中文，体现不出跨语言差异，所以要构造：

| 查询 | `lexical` | `vector` | `hybrid`（二期） |
|---|---|---|---|
| 密钥多久轮换一次？（中文查英文文档） | 无命中 | `security.md>Key rotation` 0.554 | `security.md>Key rotation` 0.500 |
| 日志要保存多久？（同义改写） | `governance.md` 0.107 | `governance.md` 0.754 | `governance.md` 1.000 |
| How long are audit logs kept?（英文查中文文档） | 无命中 | `governance.md>日志保留` 0.658 | `governance.md>日志保留` 0.500 |

`./docs` 全量首建索引约 5.7s，之后检索约 0.04s，新进程不重复嵌入（`重嵌入 0 个文件`）。

**二期也已落地**（原计划的「混合检索 + 重排」）：新增 `hybrid` 后端，词面与语义两路并发召回后用
RRF 融合（k=60，可配权重）。要解决的正是第 9 节里提到的「精确匹配（代号、编号）会被语义平滑掉」——
目标片段在词面通道会排到头部，融合后排名自然被抬起。
**cross-encoder 重排刻意没做**：那要再挂一个 ONNX 模型（体积与首次加载成本都不小），
而上面的失效模式用 RRF 已经覆盖；需要倾斜两路话语权时用权重旋钮即可。

**容量治理做了一半**：`npm run knowledge:reindex [--check]` 提供了**重建**与**对账**——
对账会报告「磁盘有、索引没跟上」与「索引有、磁盘已删」两类漂移，重建则在索引可疑时丢掉整表重来。
实测：改过 `docs/` 里一个文件后，`--check` 立刻报出该文件待重新嵌入；重建 4 个文件 111 个片段耗时 17.0s
（这个数字也说明为什么**不能**靠重建解决日常问题——增量同步才是主路径）。
第 8 节的缺陷清单与第 9 节的容量模型对应「目标形态」，
其中**分区与增量压实未做**；一旦片段规模进入百万量级，第 9 节的结论（内存决定一切）就会重新变成选型依据。

**三期刻意没做**：对象存储与解析 Worker 是为「二进制文档 + 多租户 + 异步解析」准备的。
本项目是单机、单租户、源文件就在文件系统里，`npm run knowledge:add` 已经覆盖了二进制格式的转换；
上对象存储只会多出一层需要对齐的副本，收益为负。

配置：`MINIAGENT_KNOWLEDGE_BACKEND=vector`、`MINIAGENT_EMBEDDING_LOCAL_MODEL_PATH=./models`、
`MINIAGENT_EMBEDDING_DTYPE=q4`、`MINIAGENT_VECTOR_DB_PATH=./vector-db`，
模型用 `npm run model:fetch` 下载（带 `Range` 断点续传）。
