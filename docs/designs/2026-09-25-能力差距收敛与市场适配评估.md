# 能力差距收敛与市场适配评估（2026-09-25）

本次工作的起点是一次与市场主流 Agent 框架的逐项比对，产出两份清单：

- **A. 真实缺口**——市场普遍具备、而本项目确实没有的能力（协议、持久化、模型接入、可观测标准、流式粒度）
- **B. 定位差异**——本项目有意采取的另一种做法（编排模型、协作方式、交付形态、依赖策略）

A 类逐项补齐，B 类逐项判断「跟进还是保留」。本文记录**判断依据与取舍**，
具体实现细节见 [主设计文档](../superpowers/specs/2026-09-23-miniagent-design.md)。

对比基准（2026-09 时点）：LangGraph、CrewAI、Microsoft Agent Framework 1.0、OpenAI Agents SDK、
Mastra、Vercel AI SDK、Google ADK。

---

## 0. 结论速览

| # | 项 | 归类 | 决策 | 理由一句话 |
|---|---|---|---|---|
| A1 | MCP 客户端 | 真实缺口 | **已补齐** | 工具生态的事实标准，2026-07-28 规范转为无状态核心后接入成本大幅下降 |
| A2 | 持久化执行 / 断点续跑 / 人工审批 | 真实缺口 | **已补齐** | 长任务与有副作用的工具必须能中断、能续跑、能等人批 |
| A3 | 多模型服务商接入 | 真实缺口 | **已补齐** | 单一厂商绑定是部署风险；OpenAI 兼容已成事实标准，抽象代价极低 |
| A4 | 可观测标准（OpenTelemetry） | 真实缺口 | **已补齐** | 自研 JSONL 只能自己看；OTLP 才能进现有监控体系 |
| A5 | token 级流式 | 真实缺口 | **已补齐** | 首字节延迟直接决定体感；且 tool_calls 分片必须自己拼 |
| B1 | 编排模型（图 / 角色 / 分布式） | 定位差异 | **部分跟进**：角色化 + 并行派发 | 图编排与分布式对当前规模是过度设计；但"角色"与"并发"是真实收益 |
| B2 | 交付形态（多实例） | 定位差异 | **部分跟进**：指标 OTLP 导出 + 会话可搬运 | 不引入外部存储依赖的前提下，先把"可导出"这条通路打通 |
| B3 | 生态依赖 | 定位差异 | **保留，不优化** | 核心仅 2 个依赖是可验证的优势，不是缺口 |
| B4 | 多智能体协作（handoff / 辩论） | 定位差异 | **暂不跟进** | 与本项目的"隔离式委派"是两种范式，混用会两头不讨好；见 §4 |
| B5 | 护栏（guardrails） | 定位差异 | **暂不跟进** | 已有 HITL 审批这条人工闸门；自动护栏的价值取决于具体合规要求 |

## 1. A 类：真实缺口的收敛

### A1 MCP 客户端

**市场做法**：主流框架都把 MCP 作为工具来源之一，配置格式统一为 `{"mcpServers": {...}}`。

**实现**（`src/mcp/`）：

| 文件 | 职责 |
|---|---|
| `config.ts` | 读 `mcp.json`；逐项校验 `command` 与 `url` 二选一、服务名白名单校验；文件缺失/非法只记日志不抛错 |
| `client.ts` | `McpConnection`（连接、列工具、调用、关闭）+ `McpTool implements BaseTool`，把远程工具伪装成本地工具 |
| `index.ts` | `registerMcpTools()`：并发连接各服务、失败只警告跳过、重名工具跳过；返回可 `close()` 的句柄 |

**关键取舍**：

- **不进默认依赖路径**：MCP SDK 装进来会拖进 79 个包（express / hono / ajv / jose…）。
  因此只引类型 + 动态 `import()`，`mcp.json` 不存在时 SDK 完全不加载——默认路径依赖数量不变。
- **工具名加前缀**：远程工具注册为 `mcp__<server>__<tool>`，避免与内置工具撞名。
- **安全边界写进文档**：MCP 工具在**本进程之外**执行，不受 `workspace` 文件沙箱约束；
  需要沙箱的工具应走内置实现，或把整个服务放进容器。

**验证**：`tests/mcp.test.ts`（13 例，含真实子进程端到端：用官方 SDK 起一个 stdio 服务端，
连上、注册、调用成功）；真实运行中模型自主调用 `mcp__echo__echo` 并正确回灌。

### A2 持久化执行：运行存档 + 断点续跑 + 人工审批

**市场做法**：LangGraph 的 checkpointer + time-travel，各家都把「中断恢复」当基座能力。

**实现**：

| 层 | 改动 |
|---|---|
| 存档（`src/agent/checkpoint.ts`） | `RunCheckpoint`（消息序列 + 迭代数 + 用量 + 审批决定 + 待批调用）；临时文件 + `rename` 原子替换；runId 白名单防路径穿越 |
| 主循环（`src/agent/agent.ts`） | 拆出 `reason` / `act` / `observe`；每轮工具结果回灌后落一次存档；成功即删档（磁盘只留「确实需要人看一眼」的运行） |
| 审批 | `MINIAGENT_APPROVAL_TOOLS` 列出的工具执行前挂起，抛 `ApprovalRequiredError`（**不是失败，是可继续的暂停**） |
| 服务端 | `GET /api/runs` 列可续跑运行；`POST /api/approve` 只写决定；续跑由客户端再发 `/api/chat {resume_run_id}` |
| CLI | `/runs` 与 `/resume <run_id>`；撞上审批就地问 `y/N`（默认拒绝） |

**三个容易做错的点，都做了处理**：

1. **落盘时机**：稳定点必须选在「一批工具结果全部回灌之后」——此时消息序列满足
   assistant(tool_calls) 与 tool 结果严格配对，恢复后不会出现悬空的 tool_call。
2. **`iterations` 语义**：存档里记的是「已完成轮数」，所以 `ctx.iterations++` 必须在
   `saveCheckpoint` **之前**，否则恢复后会重复计一轮。
3. **决策先落盘再读存档**：`recordApproval()` 先写、再 `loadCheckpoint()`。
   两步之间进程重启时，决定不会丢——这正是服务端把审批拆成两个接口的原因。

**整批语义**：同一批工具往往基于同一份判断发起，批准一个而偷跑另一个没有意义。
因此审批以**整批**为单位：只要批里有未决的工具，整批停下；被拒的调用不执行，
并以 `"用户拒绝执行该工具调用…"` 作为工具结果回灌，让模型改走别的路子。

**验证**：`tests/checkpoint.test.ts`（13 例：挂起不执行 / 批准后执行 / 拒绝后模型知情 /
跨实例续跑 / 从工具结果处续跑 / 成功不留档 / 关开关后不续跑）。

### A3 多模型服务商（OpenAI 兼容）

**市场做法**：Vercel AI SDK / Mastra 等一律内置多家 provider，且都以 OpenAI 协议为最大公约数。

**实现**：

- `src/llm/deepseek.ts` → `src/llm/openai.ts`，类名 `DeepSeekClient` → `OpenAICompatibleClient`。
  只依赖协议本身（`POST {baseUrl}/chat/completions` + tool calling），不再绑定任何厂商。
- `src/core/providers.ts`：预设表提供**接入点与默认模型名**，不是一个 provider 一个适配器。
  内置 `deepseek` / `openai` / `moonshot` / `dashscope` / `zhipu` / `ollama` / `custom`。
- 配置：`MINIAGENT_PROVIDER` 选预设，`MINIAGENT_BASE_URL` / `MINIAGENT_MODEL` 可覆盖；
  `MINIAGENT_API_KEY`（旧的 `MINIAGENT_DEEPSEEK_API_KEY` 继续可用）。
- 配置错误在**启动时**报出：未知 provider 列出候选；缺 baseUrl / 缺模型名直接说明缺哪个变量——
  而不是带着空值跑到第一次请求才炸。

**两个细节**：

- **本地端点不强制 Key**：`ollama` 之类的 localhost 端点不校验凭据，此时不发 `Authorization` 头。
- 未列出的服务商无需改代码：`MINIAGENT_PROVIDER=custom` + 两个变量即可接入。

**验证**：`tests/llm.test.ts` 的协议用例 + provider 配置用例（未知 provider、custom 缺址、旧变量兼容）。

### A4 可观测标准：OTLP/HTTP 导出

**市场做法**：OpenTelemetry GenAI 语义约定（`gen_ai.*`）+ OTLP 导出，接上就能进现有监控体系。

**实现**（`src/observability/otel.ts`）：**手写 OTLP/JSON 编码，不引 `@opentelemetry/sdk-*`**。
理由：要做的只有「把已有结构化事件转成 span/metric 并 POST」，而引整套 SDK 会拖进十几个包
（含 gRPC 相关）——与本项目的依赖策略相悖。OTLP/HTTP 是公开协议，一个 `fetch` 就能发。

事件 → span 的映射：

| 事件 | span | 关键属性 |
|---|---|---|
| run_start / run_end | `invoke_agent <provider>`（根） | `gen_ai.operation.name` / `gen_ai.provider.name` / `gen_ai.request.model` / `gen_ai.conversation.id` / `gen_ai.agent.name` |
| llm_start / llm_end | `chat <model>` | `gen_ai.usage.input_tokens` / `output_tokens` / `gen_ai.response.finish_reasons` / `miniagent.iteration` |
| tool_start / tool_end | `execute_tool <tool>` | `gen_ai.tool.name` / `gen_ai.tool.type` / `gen_ai.tool.call.id` |

指标（`/v1/metrics`）：`gen_ai.client.token.usage`（按 `gen_ai.token.type` = input/output）、
`gen_ai.client.operation.duration`、`miniagent.agent.runs`（按 outcome）、`miniagent.agent.run.duration`。

**三个必须做对的地方**：

1. **子 agent 中继会让 run 级事件"冒名"**：中继事件带的是**父** runId（否则进不了父轨迹），
   若照单全收，子 agent 的 `run_start/run_end` 会覆盖父的根 span，最后父运行反而没有根 span。
   因此 run 级事件按 `from_subagent` 标记跳过；模型/工具调用保留，并用 `sub_run_id` 参与配对键，
   避免并发的多个子 agent 互相顶掉。
2. **观测失败绝不影响主流程**：导出异常只记警告（含"已丢弃 N 个 span"）。
3. **长跑进程必须有定时上报**：只靠退出时上报等于没有指标，因此加了 `MINIAGENT_OTEL_METRICS_INTERVAL`
   （默认 60s，`unref()` 不钉住进程）。

端点/服务名优先读 `MINIAGENT_OTEL_*`，回退到官方变量 `OTEL_EXPORTER_OTLP_ENDPOINT` /
`OTEL_SERVICE_NAME` / `OTEL_EXPORTER_OTLP_HEADERS`——容器里通常已经按 OTel 规范注入了后者。

**验证**：`tests/otel.test.ts`（23 例：报文路径与请求头、span 树与父子关系、GenAI 属性、
取值编码 intValue/doubleValue、失败置 error、子 agent 中继、指标分桶与数据点、导出失败被吞）。

### A5 token 级流式

**实现**：`OpenAICompatibleClient.chatStream()` + `StreamAccumulator`。

两个必须处理的细节：

- **分片不等于事件**：一个 TCP 包可能包含多条 SSE 事件，也可能把一条 JSON 切成两半。
  因此按空行切事件、把尾部不完整数据留到下一个 chunk；`\r\n\r\n` 与 `\n\n` 两种分隔风格都归一化。
- **tool_calls 是分片下发的**：同一 `index` 会来多条增量（先给 id/name，再一段段给 arguments），
  必须按下标累积后一次性 `JSON.parse`。数组下标可能跳跃，所以按 index 落位而不是 push。

**降级与重试语义**：

- 少数网关不认识 `stream_options` 直接回 4xx → 去掉它再试一次（只降一次，代价是拿不到 usage）。
- **已经吐过片段就不再重试**：重试会让前端看到重复文本，只能如实失败。
  没吐过片段时按普通请求重试。
- 坏分片只跳过它自己（记一条警告），不毁整条流。
- 流式增量**不落盘**：逐 token 写 JSONL 会让轨迹膨胀几个数量级，完整文本在随后的 `llm_end` 里已有。

**前端**：`llm_delta` 事件 → 卡片内的实时文本块（带光标动画）。轮次结束时收起：
有工具调用则该轮文本会进「思考」折叠区；是最终答案则保留到 `final` 用渲染后的 Markdown 无缝替换。

**实测**（真实 DeepSeek 端点，`POST /api/chat`）：

```
event: llm_delta  data: {"text":"stream"}
event: llm_delta  data: {"text":"ing"}
event: llm_delta  data: {"text":" works"}
event: llm_end    data: {"content":"streaming works",...,"prompt_tokens":1752,"completion_tokens":4}
```

usage 非零即证明 `stream_options.include_usage` 被服务端接受。

## 2. B1 编排模型：角色化 + 可并行派发（部分跟进）

**市场做法**：CrewAI 的 role/goal/backstory；Microsoft Agent Framework 的 specialized agents；
LangGraph 的图节点并发扇出。

**本项目原状**：只有一个通用 `run_subagent`，串行、无角色。

**本次跟进两件事**：

1. **角色化**（`src/prompts/roles.ts`）：`researcher` / `analyst` / `critic` 三种身份。
   每个角色 = **一段补充提示词** + **一份工具白名单**。白名单是硬约束，
   复核员拿不到 `write_file`——这是「换个身份」与「换个语气」的区别。
   提示词注入方式是「在身份段后插一段」，没有角色时**段与版本号完全不变**，
   既有快照与 eval 归因不受影响。
2. **并行派发**（`run_subagents`）：2-5 个互不依赖的子任务 `Promise.all` 并发，
   逐项返回结论；**一个子任务失败不影响其他子任务的产出**（失败项带 error 字段）。

**刻意不跟进**：图编排（节点/边/条件跳转）与分布式编排（消息队列 + 多进程）。
判断依据：本项目面向单机、单进程、单用户场景，图的表达能力在此规模下不会被用到，
却会让「读一遍源码就能改」这个核心优势消失。需要图编排的场合应当直接用 LangGraph。

**白名单严格生效**：不做「白名单一个都不匹配就退回全量」的兜底——
那等于在配置错位时悄悄把写权限交回给本该只读的角色。宁可让它没有工具，也不能让角色约束失效。

**验证**：`tests/subagent.test.ts`（15 例，含并发探针：实测最大并发数为 3 而不是 1）。

## 3. B2 交付形态：指标可跨实例、会话可搬运（部分跟进）

**市场做法**：多实例部署 + 中心化存储（Postgres/Redis）+ 一方 APM 面板。

**本项目的约束**：不引入外部存储依赖（见 B3）。因此先把「可导出」这条通路打通，
而不是自己造一个分布式存储：

| 能力 | 做法 |
|---|---|
| 指标跨实例聚合 | 同一份指标同时以 Prometheus 文本（本进程）与 OTLP（推给 collector）两种形式暴露；N 个实例的数据在 collector 侧天然汇总 |
| 会话跨实例搬运 | `GET /api/sessions/:id/export` 导出整份会话；`POST /api/sessions/import` 导入（默认拒绝覆盖同名会话，`overwrite=true` 显式重建） |

导入按**系统边界**处理：字段可能是外部 JSON，逐条校验轮次，非法行丢弃而不是整份拒收；
覆盖时**先删再写**（jsonl 是追加写，不清旧文件会两段历史接在一起）。

**验证**：`tests/otel.test.ts` 的指标用例；`tests/server.test.ts` 的「会话跨实例搬运」4 例
（导出→另一实例导入、重复导入被拒、overwrite 重建、脏数据丢弃）。

## 4. B4 / B5 与「保留项」：不跟进的理由

**B3 生态依赖——保留，不优化。**
核心运行时依赖只有 zod + zod-to-json-schema；LanceDB / transformers.js / MCP SDK 全部是
「只引类型 + 动态 import()」的可选依赖。这不是缺口而是可验证的优势：
把 `node_modules/@lancedb` 整个移走后词面检索照常工作。任何以「生态丰富」为名引入
默认依赖的改动，都应先回答「能不能做成可选加载」。

**B4 多智能体协作（handoff / 辩论）——暂不跟进。**
OpenAI Agents SDK 的 handoff 是「把控制权与上下文交给另一个 agent」，
本项目是「派一个隔离的子 agent，只收回结论」。两者范式不同：

- handoff 适合**对话式前台**（转接给专精角色，用户继续与新的 agent 对话）；
- 隔离式委派适合**探索式后台**（父要的只是一个结论，中间过程是噪声）。

混用会同时丢掉两者的好处——既保不住上下文干净，也做不好角色连续性。
若将来要支持 handoff，应当作为一个**独立编排模式**引入，而不是把 `run_subagent` 改成它。

**B5 自动护栏（guardrails）——暂不跟进。**
已有 `MINIAGENT_APPROVAL_TOOLS` 这条人工闸门。输入/输出自动护栏的价值高度依赖具体合规要求
（行业、数据分级、部署形态），在通用框架里做一套「猜需求」的规则收益很低。
定位是：需要的人在工具层加一个 `defineTool` 包装即可，不必进内核。

## 5. 遗留与后续优先级

| 优先 | 事项 | 触发条件 |
|---|---|---|
| 高 | 用真实 collector（Jaeger/Tempo）验证 OTLP 落地 | 有监控环境时；当前只验证了报文正确性 |
| 高 | checkpoint 换共享存储后端 | 真的要多实例共享未完成运行；届时按 B2 的思路加一个可插拔接口 |
| 中 | 流式下「已吐片段后断线」的续传 | 出现实际投诉；当前策略是如实失败 |
| 中 | 角色提示词的 eval 对照（通用 vs 三角色） | 要回答「角色化到底带来多少增益」时需要 |
| 低 | handoff 编排模式 | 出现对话式前台场景 |

**已知限制（新增）**：

| 限制 | 说明 |
|---|---|
| OTLP 导出只支持 JSON 编码 | 走 `application/json`，未实现 protobuf；绝大多数 collector 都接受 JSON |
| 未用真实 collector 验证 | 只验证了报文符合 OTLP/JSON 结构，没接过 Jaeger/Tempo |
| 运行存档是单机文件 | 跨实例共享未完成运行需要共享卷或换后端 |
| 并行子 agent 的 UI 配对是近似 | 前端按工具名配对 `tool_start` / `tool_end`；同名工具并发时可能配错显示位置（轨迹文件不受影响） |
